1. Overview

Ariba NOC Center is an open-source Network Operations Center platform designed to centralize monitoring, alerting, visibility, and operational control for infrastructure teams. The platform is built around a Docker Compose deployment model so that core services can be started consistently on a single host or adapted to more advanced environments.

1.1 Introduction

The product combines multiple best-of-breed open-source tools into a unified NOC stack: Prometheus for metrics, Alertmanager for notification routing, Grafana for dashboards, Zabbix for agent and SNMP-based monitoring, LibreNMS for discovery and network device monitoring, Suricata for intrusion detection, ELK for centralized logs, ntopng for traffic analytics, and NetBox for IPAM/DCIM inventory.

1.2 Key Features and Capabilities

Unified Monitoring Collect host metrics, device status, traffic events, and IDS logs from one deployment.
Multi-Channel Alerting Route alerts to Telegram and email through Prometheus Alertmanager and script-based integrations.
Security Telemetry Detect network events with Suricata and index them in Elasticsearch for investigation.
Operational Dashboards Visualize health, utilization, traffic, and security signals in Grafana and Kibana.
Asset and IP Inventory Track devices, addresses, and topology with NetBox and LibreNMS.
Self-Healing Support Watchdog can detect non-running containers and attempt automatic restarts.

1.3 Target Users and Audience

  • Sysadmins: deploy and operate the stack, manage host and service health, and handle upgrades.
  • Network Engineers: monitor routers, switches, SNMP-enabled devices, flows, and link-state conditions.
  • NOC Engineers: triage alerts, review dashboards, investigate log events, and execute runbook steps.
  • Security Analysts: inspect Suricata alerts, correlate events in ELK, and investigate suspicious traffic.
  • Developers / Integrators: extend configuration, build automation, and integrate external systems through APIs.

2. Quickstart / Getting Started

2.1 Installation Prerequisites

Requirement Minimum Recommended Notes
Operating System Linux Ubuntu 22.04 LTS or newer The current deployment and helper scripts assume a Linux host.
Docker Engine 24+ Latest stable Required for all containers.
Docker Compose v2.20+ Latest stable The project uses docker compose syntax.
CPU 4 cores 8 cores Elasticsearch, Grafana, and Suricata benefit from more CPU.
Memory 8 GB 16 GB or more ELK and multi-tool monitoring stacks are memory-intensive.
Disk 40 GB 100 GB SSD+ Metric retention and Elasticsearch log storage grow quickly.

2.2 Step-by-Step Quickstart

cd /path/to/ariba-noc-center
cp .env.example .env
# Edit passwords, Telegram, SMTP, and host-specific values
nano .env

# First-time bootstrap
bash scripts/setup.sh

The setup script checks Docker availability, creates required host directories, adjusts file permissions, tunes vm.max_map_count for Elasticsearch, pulls images, starts databases and Elasticsearch first, and then brings up the full stack.

5. Use Cases

5.1 Network Monitoring

Monitor network devices over SNMP using LibreNMS and Zabbix templates. Track interface health, link state, uptime, bandwidth, and device availability from a central console.

5.2 Alert Management and Incident Triage

Route Prometheus-generated alerts to Alertmanager for Telegram and email delivery. Use Grafana dashboards and Kibana search to validate whether an alert is isolated or part of a wider incident.

5.3 Server Uptime and Resource Tracking

Track CPU, memory, disk, interface, and load metrics from Linux hosts through node_exporter and Zabbix agent. Detect high resource utilization or target unavailability early.

5.4 Security Monitoring

Inspect Suricata IDS alerts in Grafana or Kibana, correlate them with system logs, and investigate suspicious sources or protocols through Elasticsearch queries.

5.5 Inventory and Capacity Planning

Use NetBox for structured inventory and IP management while combining Grafana and LibreNMS metrics to make capacity, growth, and topology decisions.

6. Installation Guide

6.1 Step-by-Step Installation

  1. Install Docker Engine and Docker Compose on the target Linux host.
  2. Clone or copy the project repository to the target system.
  3. Create .env from .env.example.
  4. Set secure values for all passwords, Telegram credentials, SMTP credentials, and NetBox secret key.
  5. Run bash scripts/setup.sh.
  6. Verify service status with docker compose ps.
  7. Log into Grafana, Zabbix, LibreNMS, Kibana, and NetBox to complete environment-specific onboarding.

6.2 Configuration Files and Environment Setup

File Purpose
docker-compose.yml Defines all services, ports, environment variables, volumes, and networks.
.env Holds deployer-controlled secrets and runtime settings.
prometheus/prometheus.yml Prometheus scrape jobs, alertmanager targets, and rule includes.
alertmanager/alertmanager.yml Alert routing rules, receivers, and inhibition rules.
elk/logstash/pipeline/logstash.conf Log parsing and index selection pipeline.
elk/filebeat/filebeat.yml Input definitions for Suricata and system logs.

6.3 Docker Compose Setup

docker compose config --quiet
docker compose pull
docker compose up -d
docker compose ps

Compose creates a single bridge network named noc and attaches all services to it. Named volumes persist databases, dashboards, metrics, indices, and application state.

Implemented bootstrap path: the repository already includes scripts/setup.sh, so the preferred installation method is the scripted one rather than a purely manual sequence.

7. Configuration

7.1 Monitoring Rules

Prometheus rules live in prometheus/alerts/node.yml and prometheus/alerts/network.yml. These files define host-down, CPU, memory, disk, load, interface, traffic, packet-drop, and network error alerts. 

groups:
  - name: node_alerts
    rules:
      - alert: HostDown
        expr: up == 0
        for: 1m
        labels:
          severity: critical

7.2 Alert Routing

Alertmanager groups alerts by alertname and severity, then routes critical and warning notifications to Telegram and optionally email. Zabbix includes script-based media integrations through telegram.sh and email.sh.

7.3 Users and Permissions

  • Grafana: use built-in Grafana organization users and admin credentials from .env.
  • Zabbix: define roles, users, and media types in the Zabbix UI.
  • LibreNMS: assign user access and alert ownership through the web UI.
  • NetBox: create administrators and role-based permissions in the application.
  • Elasticsearch / Kibana: current deployment uses the elastic superuser password from .env.

8. APIs / Integration

8.1 API Surface

Ariba NOC Center is an integration platform built on multiple upstream systems. It does not currently expose a single custom API layer. Instead, integrations are performed through the APIs of embedded components.

System API Type Common Usage
Prometheus HTTP API Query metrics, targets, rules, and status data
Alertmanager HTTP API View alerts, silences, and receivers
Grafana REST API Manage dashboards, users, alerting objects, and datasources
Kibana / Elasticsearch REST API Search logs, manage indices, retrieve health, automate queries
NetBox REST API Automate IPAM/DCIM object creation and inventory synchronization
Zabbix JSON-RPC API Manage hosts, templates, triggers, and automation workflows

8.3 Integration Examples

  • Feed external dashboards from Prometheus queries.
  • Synchronize NetBox inventory into provisioning or CMDB workflows.
  • Send syslog from routers and switches to Logstash UDP port 5140.
  • Use Grafana API or provisioning files to standardize dashboards across environments.
  • Automate Zabbix host creation for newly provisioned servers.

8.4 Authentication and Security Considerations

  • Most embedded APIs inherit each upstream product's authentication model.
  • Elasticsearch security is enabled, but HTTP TLS is disabled by default in this repository.
  • Store API tokens and credentials outside version control, preferably in secrets management.
  • Restrict access to API endpoints through network segmentation or a reverse proxy.

9. Maintenance and Troubleshooting

9.1 Log Locations

Source Location Notes
Docker container logs docker compose logs -f <service> Primary troubleshooting entry point for all services.
Suricata logs suricata/log/eve.json, suricata/log/fast.log IDS event output consumed by Filebeat.
Host system logs /var/log/host/* inside Filebeat container Mounted from the Docker host for shipping.
Filebeat logs /var/log/filebeat inside container Enabled in filebeat.yml.

9.2 Common Errors and Fixes

Elasticsearch fails to start Check vm.max_map_count. The setup script sets it to 262144. Confirm host memory is sufficient.
Prometheus targets are down Inspect docker compose ps, verify service reachability on the internal network, and check scrape target names.
No logs in Kibana Check Filebeat container logs, verify eve.json exists, and inspect Logstash parsing errors.
Telegram/email alerts do not arrive Validate .env credentials, review Alertmanager config, and inspect Zabbix alert script execution.
Suricata sees no traffic Confirm the monitored interface in suricata.yaml, host networking assumptions, and capture permissions.
NetBox or LibreNMS cannot connect to backend stores Verify database credentials in .env and check Redis, MariaDB, or PostgreSQL container health.

9.3 Upgrade Procedure

  1. Back up all named volumes and bind-mounted data.
  2. Review upstream release notes for Prometheus, Grafana, Zabbix, Elastic Stack, NetBox, and LibreNMS.
  3. Update image tags in docker-compose.yml if required.
  4. Run docker compose pull.
  5. Restart with docker compose up -d.
  6. Verify dashboards, APIs, alerts, and log indexing after restart.

10. Security

10.1 Recommendations for Securing the Platform

  • Replace all default or placeholder credentials in .env before first production use.
  • Place all web interfaces behind a reverse proxy that terminates TLS and centralizes authentication.
  • Restrict published ports to management networks or bind them to localhost when feasible.
  • Store secrets in a proper secret manager instead of flat files where possible.
  • Back up volumes regularly and encrypt backups if they contain credentials or operational data.

10.2 User Access Control

  • Use Grafana organizations and roles to separate operators from administrators.
  • Configure Zabbix media types and user groups to match escalation structure.
  • Apply NetBox permission groups for inventory editors versus read-only consumers.
  • Do not expose Elasticsearch or Kibana broadly without access restrictions.

10.3 Network Hardening

  • Use firewall rules so only trusted operators can reach the exposed web ports.
  • Segment monitoring traffic from production application traffic when possible.
  • Evaluate whether Suricata should run on a mirrored/SPAN interface instead of the default container interface.
  • Review Docker socket exposure used by watchdog, because it grants broad control over the Docker host.
Current repository posture: Elasticsearch security is enabled, but TLS is disabled; Suricata runs privileged; Filebeat runs as root; watchdog mounts the Docker socket. Those are operationally understandable choices, but they should be treated as hardening priorities before production rollout.

11. FAQ

Does Ariba NOC Center expose a single unified API?

No. It is a platform assembled from multiple upstream systems. Integrations use the native APIs of Prometheus, Grafana, Zabbix, NetBox, Elasticsearch, and Alertmanager.

Can it monitor remote servers out of the box?

Partially. The current Prometheus configuration scrapes the local Node Exporter. Remote monitoring requires additional exporters, Zabbix agents, SNMP targets, or explicit scrape job entries.

Can it monitor network devices?

Yes. LibreNMS and Zabbix provide the primary path for SNMP-based device monitoring and discovery.

Is high availability included?

No. The current repository describes a single-host Compose deployment. HA would require replicated datastores, external storage, orchestration changes, and front-end failover design.

Where should I start after deployment?

Start with Grafana for dashboards, then onboard hosts and devices in Zabbix and LibreNMS, create Kibana index patterns, and load inventory into NetBox.

Is this production-ready as-is?

It is a strong functional base, but it still needs environment-specific onboarding, hardening, credentials rotation, TLS, backup design, and clear operational ownership before production use.
